# Quantum Chess for Nextcloud — Technical specification

This document is the **implementation contract** for the app. The game rules and the exact engine semantics
live in [`ENGINE-RULES.md`](ENGINE-RULES.md) (normative) and [`RULES.md`](RULES.md) (player-facing). The product and
UX design lives in [`GAME-DESIGN.md`](GAME-DESIGN.md). When this file and ENGINE-RULES.md disagree about the rules,
ENGINE-RULES.md wins; when they disagree about architecture, APIs or file layout, this file wins.

### Architecture at a glance

```
Browser (Vue SPA, #content)                                   Nextcloud server (PHP)
┌─────────────────────────────────────────┐                 ┌─────────────────────────────────────────┐
│ views/components ── composables          │  JSON/axios     │ Controllers (routes.php)                 │
│      │                   │               │ ───────────────▶│  Game / Stats / Ai / Settings / Page     │
│  src/engine (JS rules) ◀─┘               │                 │ Services                                 │
│  src/ai (Web Worker search + analysis)   │                 │  GameService ── lib/Engine (PHP rules)   │
│  src/trainer (lessons, puzzles, coach)   │                 │  RatingService, NotificationService      │
│  localStorage: local games, UI state     │                 │  Ai: LlmService → Nextcloud TaskProcessing│
└─────────────────────────────────────────┘                 │      | OpenAI-compatible | Anthropic      │
                                                             │ DB: qchess_games/moves/chat/ratings       │
                                                             │ Notifier, Dashboard widget, CleanupJob   │
                                                             └─────────────────────────────────────────┘
```

* **Online games are server-authoritative.** The browser proposes a move; PHP validates it against the PHP engine,
  applies it using `random_int` (CSPRNG) for measurements, stores the new state and returns it.
* **Local games** (vs computer, vs LLM, pass & play) run entirely in the browser with the JS engine and are persisted
  in `localStorage`. The LLM is reached through the server (API keys never leave the server).
* The **JS and PHP engines are twins**: same state JSON, same move codes, same legal-move order, same measurement
  sampling. Parity is enforced by shared fixtures (`tests/fixtures/engine/*.json`) generated by the JS engine and
  replayed by PHPUnit.

## 3. Rules engine API

The engine is **pure and synchronous**: no DOM, no network, no globals, no `Math.random()` inside (randomness is
injected). The state is a plain JSON-serialisable object whose exact schema is defined in ENGINE-RULES.md.
States are treated as immutable: functions return new objects and never mutate their inputs.

### 3.1 JavaScript (`src/engine/index.js` re-exports everything)

```js
initialState() → State
validateState(obj) → { ok: true, state } | { ok: false, error: string }     // strict: for untrusted input
generateMoves(state) → LegalMove[]            // deterministic order as specified in ENGINE-RULES.md
                                              // LegalMove = { type, from:number[], to:number[], promo?, code,
                                              //   piece:number, measured:boolean, capture:boolean,
                                              //   successProbability:number, ...extra metadata allowed }
findMove(state, moveOrCode) → LegalMove|null  // accepts a move object or a move code string
getOutcomes(state, move) → Outcome[]          // all possible results: [{ key, probability, happened, captured, state }]
applyMove(state, move, { rng?, outcome? }) → { state, move: LegalMove, measurement: Measurement|null }
        // rng: () => number in [0,1) (default Math.random); outcome: force a specific outcome key (replays)
        // Measurement = { key, probability, outcomes:[{key, probability, happened, captured}], happened, captured }
        // throws Error('illegal move') if the move is not legal
moveCode(move) → string ; parseMoveCode(code) → move|null
moveNotation(state, move, measurement?) → string   // human notation (piece letter + code, capture marks, result marks)
squareName(i) → 'e4' ; squareIndex('e4') → 28
squareView(state) → Array(64) of null | { piece, type, color, probability }
pieceLocations(state) → Map/obj piece → [{ square, probability }]
conditionalView(state, square) → Array(64) of null | { piece, probability }  // P(occupant | piece at `square`)
worldCount(state) → number
gameResult(state) → null | { result: '1-0'|'0-1'|'1/2-1/2', reason: string }
constants: MAX_WORLDS, PIECE_TYPES, START_POSITION, etc.
setupPosition(spec) → State    // build custom positions for lessons/puzzles/tests (spec format in ENGINE-RULES.md or
                               // documented in src/engine/setup.js); may include superposed pieces
```

Performance budget: `generateMoves` on a 64-world midgame state < 5 ms, `applyMove` < 2 ms in Chrome.

### 3.2 PHP (`lib/Engine/`, namespace `OCA\QuantumChess\Engine`)

A stateless service class `Engine` (injectable, no constructor dependencies) with the same operations:
`initialState(): array`, `validateState(mixed $data): array` (throws `InvalidStateException`),
`generateMoves(array $state): array`, `findMove(array $state, array|string $move): ?array`,
`getOutcomes(array $state, array $move): array`,
`applyMove(array $state, array|string $move, ?callable $rng = null, ?string $outcome = null): array`
(returns `['state' => ..., 'move' => ..., 'measurement' => ...|null]`, throws `IllegalMoveException`),
`moveCode()`, `parseMoveCode()`, `moveNotation()`, `squareName()`, `squareIndex()`, `squareView()`,
`gameResult()`, `describeForLlm(array $state): string` (textual position description used in prompts).
The default `$rng` is `fn () => random_int(0, 2**53 - 1) / 2**53`.

JSON produced by PHP must decode to exactly what the JS engine produces (floats: see ENGINE-RULES.md).

### 3.3 Parity fixtures

`tests/fixtures/generate-engine-fixtures.mjs` (run via `npm run fixtures`) plays many seeded random games with the JS
engine (including splits, merges, measurements, promotions, castling, en passant, world-cap situations) and writes
`tests/fixtures/engine/*.json`: for each step the input state, the legal move codes in order, the chosen move,
the random number used, the resulting state and measurement. PHPUnit replays every step and asserts identical
move lists and states (probabilities compared with |Δ| ≤ 1e-12, everything else exact).

## 4. Built-in AI (`src/ai/`)

* `evaluate.js` — static evaluation of a state from White's perspective (centipawns, expected value over worlds).
* `search.js` — iterative-deepening expectimax / alpha-beta for decision nodes with chance nodes for measured moves,
  move ordering, time and node limits, split-move pruning. Pure functions; unit-tested.
* `levels.js` — the 5 levels (depth/time/noise/split policy/nickname) from GAME-DESIGN.md.
* `worker.js` — Web Worker entry; message protocol `{ id, type: 'bestMove'|'analyze'|'cancel', state, options }` →
  `{ id, type: 'result'|'progress'|'error', payload }`.
* `client.js` — promise API used by the UI; falls back to running the search on the main thread in small time slices
  if Workers are unavailable:
  * `bestMove(state, { level, timeMs? }) → Promise<{ move: LegalMove, score, depth, candidates: [{ move, score }] }>`
  * `analyze(state, { timeMs?, depth?, multiPv? }) → Promise<{ score, winProbability, best: [{ move, score, pv }], threats: [...] }>`
  * `cancelAll()`

## 5. Backend

### 5.1 Database (migration `Version1000Date20260923000000`)

Table and column names must respect Nextcloud limits (table ≤ 27 chars without prefix, no NOT NULL booleans — use
smallint). All timestamps are Unix seconds (bigint).

* `qchess_games`: `id` bigint PK autoincrement; `white_uid` string(64) null; `black_uid` string(64) null;
  `creator_uid` string(64); `status` string(16) (`pending` invitation, `open` open challenge, `active`, `finished`,
  `declined`, `cancelled`); `result` string(8) null; `result_reason` string(32) null; `state` text (engine JSON);
  `ply` int; `turn` string(1); `draw_offer` string(1) null; `rated` smallint default 1; `rematch_of` bigint null;
  `rematch_id` bigint null; `chat_count` int default 0; `created_at`, `updated_at` bigint; `last_move_at` bigint null.
  Indexes on white_uid, black_uid, status, updated_at.
* `qchess_moves`: `id` PK; `game_id` bigint; `ply` int; `uid` string(64); `move` text (JSON move object);
  `code` string(64); `notation` string(64); `measurement` text null (JSON); `created_at` bigint.
  Unique index (game_id, ply).
* `qchess_chat`: `id` PK; `game_id` bigint; `uid` string(64); `message` string(1000); `created_at` bigint. Index game_id.
* `qchess_ratings`: `id` PK; `uid` string(64) unique; `rating` int default 1200; `games`, `wins`, `losses`, `draws` int
  default 0; `local_stats` text null (JSON: results vs engine levels and LLM); `updated_at` bigint.

The LLM move endpoint does **not** validate the returned code against the rules: the client validates it with the
JS engine, asks again once with `feedback` if it is illegal, and otherwise falls back to the built-in engine. This keeps
the endpoint stateless and lets Nextcloud AI tasks run asynchronously. The server still validates the incoming
`state` strictly (`Engine::validateState`) before describing it in a prompt.

Rate limits: `#[UserRateLimit(limit: 120, period: 3600)]` on `ai#move` / `ai#coach` (admin-configurable limit is
enforced additionally by `LlmService`), `#[UserRateLimit(limit: 30, period: 60)]` on chat, 60/min on game creation.

### 5.3 Game flow rules (server)

* Invitations: `POST /api/games` with an opponent creates `pending`; the opponent gets a notification with
  Accept/Decline actions. Accepting makes it `active`. Only the invitee can accept/decline, only the creator can
  cancel. Invitations expire after 14 days (CleanupJob). Users may only invite users they could share with
  (use `OCP\Collaboration\Collaborators\ISearch` in the frontend via the core autocomplete endpoint; the backend
  checks the user exists and is not the requester).
* Open challenges (`opponent: null`) are `open` until someone joins.
* Moves: participant, correct turn, game `active`, `ply` matches (optimistic concurrency via
  `UPDATE ... WHERE id = ? AND ply = ?`), move legal per PHP engine. After the move: store state, insert move row,
  clear a pending draw offer by the mover's opponent? (a move by the player who received the offer declines it),
  detect game end (engine result), update ratings (Elo, K = 32, only when `rated`), send notifications.
* Resign/draw/abandon: finished with reason. Active games with no move for 30 days are finished as `abandoned`
  (loss for the side to move) by CleanupJob.
* Notifications (`Notifier`, subjects): `invite`, `accepted`, `declined`, `your_turn` (one per game, replaced on each
  move), `game_over`, `draw_offer`, `rematch`. Links point to `/apps/quantumchess/#/game/{id}`. Dismiss obsolete
  notifications (`INotificationManager::markProcessed`) when the user acts.
* Dashboard widget (`IAPIWidgetV2` + `IIconWidget` + `IButtonWidget` + `IReloadableWidget`): games where it is your
  turn and incoming invitations.

### 5.4 LLM integration (`lib/Service/Ai/`)

Providers (`ProviderInterface::complete(string $system, string $user, array $options): string`):
* **Nextcloud** — `OCP\TaskProcessing\IManager`, task type `core:text2text` (`TextToText::ID`), scheduled
  asynchronously (`scheduleTask`) with `appId = quantumchess` and `customId = move|coach`; results fetched with
  `getUserTask()`. The model is whatever the admin configured in *Administration settings → Artificial
  intelligence*; we show the name of the preferred provider.
* **OpenAI-compatible** — `POST {baseUrl}/chat/completions` (Bearer key), `GET {baseUrl}/models`. Presets: OpenAI,
  Mistral, OpenRouter, Groq, Google Gemini (OpenAI-compatible endpoint), Ollama, LocalAI/LM Studio, custom.
* **Anthropic** — `POST https://api.anthropic.com/v1/messages` with `x-api-key`, `anthropic-version: 2023-06-01`;
  `GET /v1/models`. Suggested default model: `claude-sonnet-5` (fast/cheap alternative: `claude-haiku-4-5`).
* Uses `OCP\Http\Client\IClientService` with timeouts (connect 10 s, total 90 s). Local/private addresses are only
  allowed when the admin enabled "Allow local AI servers" (`'nextcloud' => ['allow_local_address' => true]`).
* Key storage: `AiConfigService` encrypts keys with `OCP\Security\ICrypto` and stores them in app config (shared key)
  or user config (personal key). Keys are never returned to the browser (only `hasKey` and the last 4 characters).
* Prompts: `PromptBuilder` builds the system prompt (persona, rules summary, output format) and the user prompt
  (`Engine::describeForLlm`, recent moves, legal move codes, optional engine hints, optional feedback). The answer must
  be JSON `{"move": "<code>", "comment": "<≤ 200 chars>"}`; the parser tolerates code fences and extra text.
  Coach answers are Markdown, ≤ 250 words, in the user's language.

### 5.5 Settings

* **Admin** (Administration settings → Quantum Chess): `nextcloud_ai_enabled` (default true), `shared_enabled`,
  shared provider `{kind, preset, baseUrl, model, apiKey}`, `allow_personal_keys` (default true),
  `allow_local_servers` (default false), `leaderboard_enabled` (default true), `ai_requests_per_hour` (default 60).
* **Personal** (Personal settings → Quantum Chess): own provider `{kind, preset, baseUrl, model, apiKey}` (if allowed),
  default AI source, test connection + model list.
* **In-app preferences** (stored as JSON user config, delivered as initial state `preferences`): board theme, piece
  set, sound on/off + volume, animation speed, show percentages, heat map, coordinates, coach on/off, confirm
  moves, default engine level, default persona.

Initial state (`OCP\AppFramework\Services\IInitialState`) provided by `PageController::index`:
`preferences`, `user` `{ uid, displayName }`, `features` `{ nextcloudAi, personalKeys, sharedKey, leaderboard,
aiAvailable }`, `appVersion`.

## 6. Frontend

* `src/main.js` mounts `App.vue` on `#content`; `router.js` uses `createWebHashHistory()`.
* Routes: `/` Home (lobby), `/play/:mode(computer|ai|local)/:id?` local game, `/game/:id` online game,
  `/review/:source(local|online)/:id` review, `/trainer`, `/trainer/lesson/:lessonId`, `/trainer/puzzle/:puzzleId`,
  `/rules`, `/stats`.
* `App.vue`: `NcContent app-name="quantumchess"` → `AppNavigation.vue` (New game, Home, Trainer, Rules, Statistics,
  list of online games with "your turn" counter bubbles, settings dialog) + `NcAppContent` with `<router-view>`.
* **QuantumBoard.vue** (the heart of the UI) props: `state`, `legalMoves`, `orientation` (`'w'|'b'`), `interactive`,
  `playerColor` (`'w'|'b'|null` = both), `lastMove`, `mode` (v-model: `'move'|'split'|'merge'`), `arrows`
  (`[{from,to,color}]`), `highlights`, `preferences`; emits `move` (a LegalMove) and `select`. It implements all
  input handling (click/tap, drag, keyboard) and quantum visualisation (probability badges, opacity, other locations,
  entanglement view, heat map) and the measurement animation (`playMeasurement(measurement)` exposed method).
* Services: `api.js` (one function per route, returns `response.data`), `preferences.js` (reactive, debounced save),
  `localGames.js` (save/load/list/delete local games in `localStorage`, versioned), `sound.js` (WebAudio-synthesised
  sounds, no audio files), `format.js` (notation, percentages, relative time).
* All user-visible strings use `t('quantumchess', '...')` / `n(...)` from `@nextcloud/l10n`; PHP uses `IL10N`.
* Icons: `@mdi/js` paths rendered with `NcIconSvgWrapper`.
* Styling: Nextcloud CSS variables only (`--color-main-background`, `--color-primary-element`, `--border-radius-large`,
  ...), scoped styles, works in light/dark/high-contrast themes. No external fonts or CDNs (CSP).
